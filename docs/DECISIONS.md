## ADR-001 — ใช้ Laravel 12 แทน Laravel 11

**วันที่:** 2026-08-26 · **สถานะ:** อนุมัติแล้ว

**บริบท**
สเปกข้อ 1 ระบุ Laravel 11.x แต่ติดตั้งไม่ผ่าน — Composer 2.10 บล็อกแพ็กเกจที่มี security advisory ค้างอยู่

**หลักฐาน** (จาก Packagist security advisory API)

| Advisory | ช่วงที่กระทบ | เวอร์ชันที่แก้ |
|---|---|---|
| `PKSA-mdq4-51ck-6kdq` — CRLF injection in default email rule | `>=11.0.0,<12.0.0` · `<12.60.0` · `<13.10.0` | **ไม่มีในสาย 11** |
| `PKSA-m5cs-t1y6-qpcs` — Temporary Signed URL path confusion | `<12.61.1` · `>=13.0.0,<13.12.0` | 12.61.1 / 13.12.0 |

สาย 11 ทั้งสาย (ถึง v11.56.1 ซึ่งเป็นตัวสุดท้าย) ไม่มีเวอร์ชันที่แก้ `PKSA-mdq4-51ck-6kdq` — หมดช่วง security support แล้ว

**การตัดสินใจ**
ใช้ **Laravel 12.x** (ติดตั้งจริง 12.68 — `composer` รายงาน `No security vulnerability advisories found`)

**เหตุผล**
- การยึด Laravel 11 = ส่งของพร้อมช่องโหว่ที่ไม่มีวันถูกแพตช์ ขัดกับ checklist ข้อ 8 โดยตรง
- Laravel 12 ห่างจากสเปกเพียง 1 major และเข้ากันได้กับโค้ด Laravel 11 เกือบทั้งหมด
- แพ็กเกจที่สเปกกำหนดรองรับครบ: `spatie/laravel-permission ^8.3` · `spatie/laravel-activitylog ^4.12` · `barryvdh/laravel-dompdf ^3.1` · `maatwebsite/excel ^4.0` · `laravel/breeze ^2.4` · `pestphp/pest ^3`
- PHP 8.3 ตามสเปกยังใช้ได้ (Laravel 12 ต้องการ `php ^8.2`)

**ทางเลือกที่ไม่เลือก**
- *Laravel 13* — ใหม่กว่าแต่ต้องการ `php ^8.3` พอดีตัว และแพ็กเกจ 3rd-party บางตัวยังตามไม่ทัน
- *Laravel 11 + ปิด advisory check* — ต้องใส่ `policy.advisories.ignore-id` และรับความเสี่ยง CRLF injection ไว้เอง

## ADR-002 — เก็บสถานะ "ถูกแทนที่" ด้วยคอลัมน์ `superseded_at`

**วันที่:** 2026-08-26 · **สถานะ:** อนุมัติแล้ว

**บริบท**
สเปกข้อ 4.3 พูดถึง flag `superseded` ตอนสร้าง revision แต่ enum `status` ในข้อ 3.3 ไม่มีค่านี้

**การตัดสินใจ**
เพิ่มคอลัมน์ `quotations.superseded_at` (timestamp, nullable) แยกจาก `status`

**เหตุผล**
- ใบที่ถูกแทนที่ยังคง `status = sent` ไว้ได้ → สถิติ win rate และรายงานยอดเสนอราคาไม่เพี้ยน
- รู้ได้ว่าถูกแทนที่ "เมื่อไหร่" ไม่ใช่แค่ "ถูกแทนที่แล้ว"
- ไม่ต้องแก้ query ทุกที่ที่กรอง `status = sent`

## ADR-003 — เพิ่ม role `sales_manager`

**วันที่:** 2026-08-26 · **สถานะ:** อนุมัติแล้ว

**บริบท**
สเปกข้อ 3.1 ระบุ 5 roles (`admin`, `sales`, `warehouse`, `engineer`, `viewer`) แต่ข้อ 8 อ้างถึง "manager" ที่เห็นใบเสนอราคาของทุกคน และข้อ 4.3 ต้องมีคนอนุมัติใบที่เข้าเกณฑ์

**การตัดสินใจ**
เพิ่ม role ที่ 6 ชื่อ `sales_manager` — อนุมัติใบเสนอราคาได้ และเห็นใบของ sales ทุกคน

**เหตุผล**
แยกสิทธิ์เชิงธุรกิจ (อนุมัติราคา) ออกจากสิทธิ์เชิงเทคนิค (`admin` = ดูแลระบบ) ตามหลัก least privilege

## ADR-004 — ข้อมูลตั้งต้นเป็นข้อมูลสมมติ

**วันที่:** 2026-08-26 · **สถานะ:** อนุมัติแล้ว

**บริบท**
สเปกข้อ 10 เฟส 1 ขอ seeder 30 SKU จริงของ TEXSON และข้อ 5 ขอโลโก้/ลายเซ็น/เลขผู้เสียภาษีจริง

**การตัดสินใจ**
Seeder ใช้ข้อมูลสมมติที่สมจริงตามหมวดหมู่จริง (UPS, Battery, CRAC, PDU ฯลฯ) · ข้อมูลบริษัทเก็บในตาราง `settings` ให้แก้ผ่านหน้าตั้งค่าได้โดยไม่ต้อง deploy ใหม่

**เหตุผล**
ราคาทุน/ราคาขายจริงเป็นข้อมูลอ่อนไหว ไม่ควรอยู่ใน git · การผูกข้อมูลบริษัทไว้ใน `settings` ทำให้เปลี่ยนโลโก้/ที่อยู่/ลายเซ็นได้เองภายหลัง

## ADR-005 — เพิ่มตารางใบรับสินค้าและใบโอนคลัง

**วันที่:** 2026-08-26 · **สถานะ:** อนุมัติแล้ว

**บริบท**
สเปกข้อ 3.2 ระบุว่า `stock_movements.ref_type` ชี้ไปยัง **Delivery, PurchaseReceipt, StockAdjustment** แต่ schema ของ Phase 1 มีเพียง `stock_adjustments` — ไม่มีโครงสร้างของ `PurchaseReceipt` และแผนเฟส 2 ที่ระบุ "โอนคลัง" ก็ไม่มีตารางรองรับ

**การตัดสินใจ**
เพิ่มเอกสารคลังสองชุด พร้อมเลขรันนิ่งของตัวเอง

| ตาราง | เลขเอกสาร | ทำอะไรตอน post |
|---|---|---|
| `goods_receipts` + `goods_receipt_items` | `GR-YYYYMM-####` | เขียน ledger `receive` และสร้าง serial |
| `stock_transfers` + `stock_transfer_items` | `TR-YYYYMM-####` | เขียน ledger `transfer_out` + `transfer_in` และย้ายคลังของ serial |

ทั้งคู่มีสถานะ `draft → posted | cancelled` เหมือน `stock_adjustments`

**เหตุผล**
- ยอดในคลังทุกชิ้นต้องตอบได้ว่ามาจากเอกสารใบไหน — รับเข้าแบบไม่มีเอกสารจะย้อนกลับไม่ได้ว่ารับจาก PO ไหนและใครตรวจรับ
- `goods_receipts` คือสิ่งที่สเปกเรียกว่า `PurchaseReceipt` จึงเติมช่องว่างของ schema เดิมโดยไม่ขัดกับที่เขียนไว้
- การเบิกของขึ้นสต็อกรถบริการ (`VAN`) ต้องรู้ว่าใครเบิกไปและเมื่อไร ใบโอนจึงจำเป็น ไม่ใช่ของฟุ่มเฟือย

## ADR-006 — สินค้าที่ติดตาม serial ต้องกรอก serial ครบตอนรับเข้า

**วันที่:** 2026-08-26 · **สถานะ:** อนุมัติแล้ว

**บริบท**
สเปกข้อ 4.4 บังคับเลือก serial ตอน post ใบส่งของ แต่ไม่ได้ระบุว่าตอนรับเข้าต้องกรอกหรือไม่

**การตัดสินใจ**
`GoodsReceiptService::post()` ตรวจก่อนแตะสต็อกว่าจำนวน serial เท่ากับจำนวนที่รับพอดี ถ้าไม่ครบจะโยน `SerialNumberMismatchException` และไม่รับเข้าเลยแม้แต่บรรทัดเดียว

**เหตุผล**
- ถ้ายอมให้รับเข้าโดยไม่มี serial จำนวน serial สถานะ `in_stock` จะไม่ตรงกับ `qty_on_hand` แล้วตอนส่งของจะเลือก serial ไม่ครบ — ปัญหาจะไปโผล่ตอนของกำลังจะออกจากคลัง ซึ่งแก้ยากกว่ามาก
- ตรวจทุกบรรทัดก่อนเขียน ledger ทำให้ไม่เกิดสภาพ "รับเข้าไปครึ่งใบแล้วค้าง"

**ผลข้างเคียงที่ยอมรับ**
หน้าจอรับเข้าใช้เวลานานขึ้นสำหรับสินค้าที่มี serial จำนวนมาก — บรรเทาด้วยช่องกรอกแบบหลายบรรทัดพร้อมตัวนับ `กรอกแล้ว / ต้องการ` แบบเรียลไทม์

## ADR-007 — ยอดสต็อกตั้งต้นสร้างผ่านใบปรับปรุง ไม่ใช่ INSERT ตรง

**วันที่:** 2026-08-26 · **สถานะ:** อนุมัติแล้ว

**บริบท**
`OpeningStockSeeder` ต้องตั้งยอดสต็อกตัวอย่างบนเครื่องพัฒนา

**การตัดสินใจ**
Seeder สร้างใบปรับปรุงเหตุผล `opening` แล้วสั่ง post ผ่าน `StockAdjustmentService` แทนการเขียน `stock_levels` ตรง ๆ

**เหตุผล**
DoD ของเฟสนี้คือยอดคงเหลือต้องเท่ากับผลรวม ledger เสมอ ถ้า seed ด้วยการ INSERT ยอดตั้งต้นจะไม่มีที่มาใน ledger แล้ว invariant พังตั้งแต่แถวแรก — เท่ากับสร้างข้อมูลตัวอย่างที่พิสูจน์อะไรไม่ได้

## ADR-008 — สคริปต์ PowerShell ต้องเป็น ASCII ล้วน

**วันที่:** 2026-08-26 · **สถานะ:** อนุมัติแล้ว

**บริบท**
`scripts/db-start.ps1` ที่เขียนคอมเมนต์และข้อความเป็นภาษาไทยรันไม่ได้บนเครื่องพัฒนา — Windows PowerShell 5.1 อ่านไฟล์ `.ps1` ด้วย ANSI codepage ของระบบเมื่อไฟล์ไม่มี UTF-8 BOM ทำให้ข้อความไทยกลายเป็นขยะและ parser พัง

**การตัดสินใจ**
สคริปต์ `.ps1` ทุกไฟล์ในโปรเจกต์เขียนด้วย ASCII ล้วน (คอมเมนต์และข้อความเป็นภาษาอังกฤษ)

**เหตุผล**
การใส่ BOM แก้ปัญหาได้แต่เปราะ — เครื่องมือที่เขียนไฟล์ทับ (editor, git filter, สคริปต์อื่น) ทำ BOM หายหรือซ้อนกันได้ง่าย ระหว่างงานนี้ก็เกิดทั้งสองกรณีจริง ส่วน ASCII ล้วนให้ผลเหมือนกันทุก encoding

> ข้อจำกัดนี้ใช้กับ `.ps1` เท่านั้น — ไฟล์ PHP, Blade และเอกสารยังเป็น UTF-8 ภาษาไทยตามปกติ
